# Архитектура API-клиентов (API_ARCHITECTURE.md)

## 1. Введение и назначение

Документ описывает архитектуру, контракты взаимодействия и механизмы отказоустойчивости клиентов внешних сервисов:
- **WEEEK REST API Client**
- **Linear GraphQL API Client**

Клиенты изолируют транспортный уровень, реализуют типизацию ответов с помощью `zod`, управляют пагинацией, повторными попытками (retry) и защитой от превышения квот (rate limiting).

---

## 2. Структура компонентов API

```
src/clients/
├── weeek/
│   ├── client.ts         # WeeekClient: реализация REST-методов с автопагинацией
│   ├── schemas.ts        # Zod-схемы валидации ответов WEEEK
│   └── types.ts          # Строго типизированные интерфейсы WEEEK
└── linear/
    ├── client.ts         # LinearClient: обертка над @linear/sdk / GraphQL
    ├── queries.ts        # Типизированные GraphQL запросы и мутации
    ├── schemas.ts        # Zod-схемы валидации сущностей Linear
    └── types.ts          # Строго типизированные интерфейсы Linear
```

## 3. Спецификация WEEEK Client

### Базовый URL и авторизация
- Базовый URL: `https://api.weeek.net/public/v1`
- Аутентификация: заголовок `Authorization: Bearer <WEEEK_API_TOKEN>`

### Эндпоинты
1. `GET /user/me` — верификация токена и получение профиля пользователя.
2. `GET /tm/projects` — получение списка проектов рабочего пространства.
3. `GET /tm/projects/:id` — получение детальной информации о проекте.
4. `GET /tm/tasks` — получение списка задач проекта с поддержкой параметров `projectId`, `offset`, `perPage`, `all`.
5. `GET /tm/tasks/:id` — получение детальной информации о конкретной задаче.
6. `GET /tm/users` / `GET /ws/users` — список пользователей рабочего пространства для сопоставления по email.
7. `GET /tm/tags` — список тегов рабочего пространства.

### Автоматическая пагинация WEEEK
Метод `getTasks` автоматически перебирает страницы, пока `hasMore === true` или количество полученных задач не достигнет общего числа, избавляя вызывающий код от ручного управления оффсетами.

## 4. Спецификация Linear Client

### Базовый эндпоинт и авторизация
- Эндпоинт: `https://api.linear.app/graphql`
- Аутентификация: заголовок `Authorization: <LINEAR_API_TOKEN>` (или Personal API Key через `@linear/sdk`).

### Запросы (Queries)
1. `viewer` — проверка подключения и получение информации о текущем пользователе/организации.
2. `teams` — получение списка доступных команд Linear (`id`, `key`, `name`).
3. `workflowStates(teamId)` — получение состояний жизненного цикла задач (`Backlog`, `Unstarted`, `Started`, `Completed`, `Canceled`).
4. `issueLabels(teamId)` — список доступных меток команды для дедупликации перед созданием.
5. `users` — список участников организации для сопоставления исполнителей по email.
6. `projects(teamId)` — список проектов команды.

### Мутации (Mutations)
1. `projectCreate` — создание проекта Linear.
2. `issueCreate` — создание задачи/подзадачи Linear (`teamId`, `title`, `description`, `priority`, `stateId`, `dueDate`, `assigneeId`, `labelIds`, `projectId`, `parentId`).
3. `issueUpdate` — обновление задачи (используется при отложенном связывании родительской задачи или статуса).
4. `issueLabelCreate` — создание новой метки на уровне команды (`name`, `color`, `teamId`).

## 5. Механизмы надежности (Resilience & Rate Limiting)

1. **Экспоненциальный Retry с джиттером**:
   - 1-я попытка: 1 с + рандомный джиттер
   - 2-я попытка: 2 с + джиттер
   - 3-я попытка: 4 с + джиттер
   - 4-я попытка: 8 с + джиттер
2. **Обработка HTTP 429 (Too Many Requests)**:
   - Автоматический парсинг заголовка `Retry-After` (в секундах или HTTP-date) и ожидание перед повтором.
3. **Классификация ошибок**:
   - **Fatal**: 401 Unauthorized, 403 Forbidden, Team Not Found — немедленная остановка.
   - **Recoverable**: 429 Rate Limit, 500/502/503/504 Server Error, Network Timeout — повтор по политике retry.
4. **Конкурентность**:
   - Использование очереди с ограничением `API_CONCURRENCY` (по умолчанию 3 одновременных запроса).
